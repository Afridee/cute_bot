# M2.5 human-bar testing guide — background survivability (on-device only)

> **Status:** M2.5 human bar **passed** (two phones, Aug 2026). CDM link
> and presence resurrection, quiet notification, watchdog / keep-alive
> alarm, Recents recovery, phone alerts on the bot, and OEM guidance.
> Keep this page as the re-run procedure. Current product status:
> `README.md`.

This guide is written for **phones in your hand, no laptop connected**. No
`flutter run`, no USB, no `adb`. Everything you observe is visible on the
screen or in the notification shade.

What M2.5 added, in the order a tester hits it:

- CompanionDeviceManager (CDM) association with device-presence wake-up
- A quieter persistent notification and an ask-once battery-optimization
  prompt
- A WorkManager watchdog (~15 min) and a keep-alive alarm (~60 s)
- A notification listener in an isolated `:listener` process — the
  keep-alive anchor on vivo/iQOO, and the input for **phone alerts on the
  bot**
- An ask-once "Keep the bot alive" guidance page on vivo/iQOO

None of this runs on an emulator (no BLE).

## What you need

| Item | When |
|---|---|
| **Companion phone** (phone #1) | Always. Android 12+ (API 31+) for §2 CDM wake-up; Android 10+ (API 29+) for everything else. |
| **Bot phone** (phone #2) | §1–§2, the full §3 link/battery path, and §7 phone alerts. Runs **Bot Simulator**. |
| **APK installed on each phone** | Once, before you unplug — see [Install the app](#install-the-app-no-laptop-during-testing) below. |
| **vivo or other aggressive OEM** | Strongly recommended for §6 and §8 — that's where Recents swipe actually kills the bot. |

### One phone vs two

| Section | Phones | Bot connected? |
|---|---|---|
| §1 CDM link | **Two** | Simulator advertising; link step pairs them |
| §2 CDM resurrection | **Two** | Was connected; you drop and restore range |
| §3 notifications (full) | **Two** | Connected — for `Connected · N% · idle` |
| §3 notifications (partial) | **One** | Not required — fake utterance still exercises silence + brain text |
| §4 watchdog | **One** | Not required |
| §5 battery prompt | **One** | Not required |
| §6 Recents / listener recovery | **One** | Not required (connected is nicer) |
| §7 phone alerts | **Two** | Connected — cyan blink + chirp on the simulator |
| §8 OEM guidance | **One** | Not required — vivo/iQOO only |

Start with **§5, §4, and §6 on one phone** if you only have the companion
device handy. Do **§1–§2 and §7 when you have two phones**. On a vivo/iQOO
companion, do **§6 and §8** — those are the tests that motivated the
listener process.

## Install the app (no laptop during testing)

You need the APK on each phone **once**. After that, testing is fully
untethered.

**On a dev machine** (any time, cable optional):

```bash
flutter build apk --debug
```

The file lands at `build/app/outputs/flutter-apk/app-debug.apk`. Copy it to
each phone however you like (AirDrop, Google Drive, Telegram, USB file copy
then unplug).

**On each phone:**

1. Open the APK → install (allow "Install unknown apps" for your file
   manager if prompted).
2. Launch **cute_bot**.
3. Pick **Bot Simulator** on phone #2, **Companion** on phone #1.

Same APK on both phones — the launcher asks which mode.

To reset §5 (battery ask-once) **and** §8 (OEM guidance ask-once):
**Settings → Apps → cute_bot → Storage → Clear data** (not just cache).
That also clears CDM link state, the transcript, and Notification-access
does *not* come back automatically — you will have to grant it again.

## On-device actions you'll reuse

These replace every `adb` step from the developer guide.

### Three different "kills" — they are not the same

| Action | What it actually does | Who recovers |
|---|---|---|
| **Home** | Leaves the UI; FGS stays. The vivo guidance page's recommended leave. | Nothing to recover. |
| **Swipe from Recents** | Stock Android: FGS is meant to survive. **vivo/iQOO:** the cleaner often SIGKILLs the default process (locking the Recents card does **not** stop an individual swipe). `:listener` and a pre-armed keep-alive alarm can still revive the FGS. | §6 |
| **Settings → Force stop** | Package FORCE_STOP: every process dies (including `:listener`), alarms are cancelled. Self-recovery needs the OS to rebind the notification listener, or you to open the app. | §2 (CDM, bot in range), §4 (watchdog), and maybe the listener if the OEM rebinds |

**(Swiping the app out of recents is *not* the same test as Force stop.)**

### Force-stop the companion app (strongest kill)

**Settings → Apps → cute_bot → Force stop**

Confirm. The persistent notification should disappear — the process is
dead. This is what §2 and §4 use.

### Recents swipe (vivo's real-world kill)

Open Recents and swipe Cute Bot away. On vivo, also try this *with* the
Recents card locked — the lock only protects against "clean all".

### Check the service is running

Pull down the notification shade. A **Cute Bot** ongoing notification means
the foreground service is up. No notification → service is down.

In the app, the Foreground service card should show **Alert access: on**
once Notification access is granted.

### Open companion without restarting the service

Tap the app's launcher icon, or tap the ongoing notification if your OEM
routes it to the app. The UI should attach and show **Service running**.

### Deliberately stop the bot (user stop)

In the app: **Stop service** on the Foreground service card. Notification
goes away and should **stay** away until you tap **Start service**.

### Toggle bot in/out of range (two-phone tests)

On the **simulator phone**: turn **Bluetooth off**, wait until the
companion Link card shows disconnected/reconnecting, then turn Bluetooth
**on** again. Walking out of the room works too; toggling BT is easier to
repeat.

### Fresh install without a laptop

**Settings → Apps → cute_bot → Uninstall**, then reinstall from the same
APK file you copied earlier.

## 0. Setup (two phones)

1. **Phone #2:** open cute_bot → **Bot Simulator** → screen shows
   **Advertising CuteBot**. Leave it on this screen.
2. **Phone #1:** open cute_bot → **Companion**. Grant **Bluetooth** and
   **Notifications** when asked. The battery-exemption dialog appears on
   first start — accept it for §4 / §6 recovery tests, or decline if you're
   deliberately testing the fallback path in §4.
3. Grant **Notification access**: Foreground service card → **Allow
   notification access** (or **Alert access: off** until you do). This is
   required for §6 and §7, and is the vivo keep-alive. The system settings
   page should list **Cute Bot** — enable it, then return; the chip should
   flip to **Alert access: on**. Leave **Show phone alerts on bot** on
   (default) for §7.
4. Wait until the **Link** card on phone #1 shows **Connected** and the
   notification shade shows something like `Connected · 87% · idle` (87% is
   the simulator's fake battery — it may take a few seconds after connect).

## 1. CDM association ("Link bot to Android") — two phones

1. On phone #1, find the **Android link (CDM)** card → **Link bot to
   Android**.
2. Expected: the **system chooser** opens and scans. The simulator phone
   should appear (matched on the bot service UUID). Select it.
3. Expected next: a **Bluetooth pairing request** on **both** phones.
   Accept on both — the phone needs the bond so it can track the bot's
   rotating BLE address (see `ble_protocol.dart`).
4. The card should show: `Linked <address>` · `Pairing: bonded` · **Wake
   on approach**.
   - Stuck on `Pairing: bonding` → pairing was dismissed; **Remove link**
     and redo §1.
   - On Android 10/11: `No wake-up (needs Android 12+)` is expected —
     association works, wake-on-approach does not.
5. **Remove link** → card returns to `Not linked`. (The Bluetooth bond may
   remain under **Settings → Bluetooth** — forget the device there for a
   clean re-test.)

**Pass:** chooser finds the simulator, bond completes, card shows linked +
bonded + wake on approach (on API 31+).

---

## 2. CDM presence resurrection — two phones, API 31+

The headline test: dead app + bot comes back in range → service resurrects
**without you opening the app**.

The service must have been **started** and **not** stopped with the Stop
button (Stop writes "user stopped"; force-stop does not).

1. Complete §1. Confirm the ongoing notification is visible.
2. On phone #2, turn **Bluetooth off**. On phone #1, wait until the Link
   card shows disconnected/reconnecting (or open the shade — link text
   changes).
3. On phone #1: **Settings → Apps → cute_bot → Force stop**. Notification
   must disappear.
4. On phone #2, turn **Bluetooth on** (bot back in range).
5. **Do not open the app.** Watch the notification shade for up to ~2
   minutes (Android's companion-device scan is opportunistic, not instant).

   **Pass:** the **Cute Bot** ongoing notification returns on its own, then
   shows connected state (e.g. `Connected · … · idle`). Optionally open
   the app — Link card should say **Connected**.

6. **Deliberate-stop control:** press **Stop service** in the app, force-stop
   again (step 3), turn simulator BT back on. **Pass:** nothing happens —
   no notification, no resurrection. A user stop must stay stopped.

**If step 5 never passes:** check the CDM card still says `Pairing:
bonded`. If not, redo §1. Presence tracking needs the bond. On vivo, also
run §6 — CDM is not the only resurrection path, and FORCE_STOP is the
hardest kill.

## 3. Notification content and silence

### Full path (two phones, connected)

1. Shade open: text looks like **`Connected · 87% · idle`** (battery
   appears after the first telemetry; before that, `Connected · idle`).
2. In the app, **Fake utterance** on the Brain card. Shade should move
   through **`thinking`** / **`responding`** and back to **`idle`** —
   **no sound, no vibration, no heads-up popup**.
3. On phone #2, Bluetooth **off** → phone #1 shade should shift toward
   **`Reconnecting · …`** within a few seconds.

### Partial path (one phone, no bot)

Service can run without a connected bot (Link card shows scanning/offline).

1. **Fake utterance** → same silence check as above; text will say
   `Looking for bot` or similar instead of `Connected`.
2. Long-press the notification → **Channel settings** → importance should
   be **Low** (or Silent on some OEMs).

### vivo specifically

During steps above: confirm zero buzzes. Then check **Settings → Battery →
Background power consumption management** (or iManager) — if cute_bot is
restricted, that's what §4's fallback notification is for.

**Pass:** never alerts audibly; triple format when connected; updates on
state change without spamming the shade.

## 4. Watchdog — one phone, patience required

A background check every **~15 minutes** restarts the service if it should
be running but isn't. There is no on-device shortcut to trigger it early —
plan for **15–30 minutes** screen-off waiting (WorkManager runs in doze
maintenance windows).

For a **faster** recovery check on the same kill, use §6 (keep-alive alarm
is ~60 s, and the listener is immediate when it survives). §4 is the slow
net that still works after a FORCE_STOP has cancelled alarms — if the OS
lets WorkManager run.

1. Open companion; confirm the ongoing notification is present. **Do not**
   press Stop.
2. **Settings → Apps → cute_bot → Force stop** (or let vivo iManager kill
   it). Notification gone.
3. Leave the phone alone (screen off is fine). Wait **at least 30 minutes**.

   **Pass — recovery:** ongoing notification returns without you opening
   the app. Likely if battery exemption was granted in §0.

   **Pass — fallback (also OK):** a **separate, dismissable** notification:
   *"Cute Bot stopped — Android blocked the background restart. Tap to
   bring the bot back."* Tap it → app opens → service restarts → ongoing
   notification returns.

   **Fail:** after 30+ minutes, nothing — no ongoing notification, no
   fallback. That's a bug.

4. **Control:** **Stop service** → force-stop → wait 30+ min. **Pass:**
   nothing happens — no ongoing notification, no fallback.

## 5. Battery prompt — ask once — one phone

1. **Clear data** or reinstall (see [Install](#install-the-app-no-laptop-during-testing)).
2. Open **Companion** with battery optimization still active for the app.
   The exemption dialog should appear **once**.
3. **Decline.** Force-stop and reopen several times — dialog must **not**
   come back on its own.
4. In the app, **Allow background** on the service card should still open
   the dialog when you choose.

**Pass:** auto-prompt exactly once per install; manual button still works.

## 6. Recents swipe + notification listener — one phone (vivo is the point)

This is the keep-alive that CDM and the 15-minute watchdog do not cover:
vivo's Recents cleaner killing the default process while the user still
wants the bot.

**Notification access must be on** (`Alert access: on`). Without it, a
vivo swipe is a FORCE_STOP-class kill and nothing we own can self-recover.

The service must have been **started** and **not** Stopped.

### 6a. Recents swipe (the everyday kill)

1. Confirm the ongoing notification is visible. Leave with **Home** first
   and check it stays — that's the control: Home must not kill the bot.
2. Open Recents and **swipe Cute Bot away**. On vivo, also try with the
   card **locked** (pull down / long-press → lock icon) — an individual
   swipe still kills.
3. **Do not open the app.** Watch the shade.

   **Pass (seconds):** the ongoing notification returns on its own. Typical
   when `:listener` survived and saw the FGS notification disappear.

   **Pass (~1–2 minutes):** notification returns via the keep-alive alarm
   (`KeepAliveReceiver`, ~60 s). Still a pass.

   **Fail:** after ~3 minutes, nothing. On stock Android this test is
   uninteresting if the FGS never died (notification never left) — that is
   also a pass, just a different OEM.

4. **Control:** **Stop service**, then Recents-swipe. **Pass:** nothing
   comes back.

### 6b. Settings Force stop, with Notification access still granted

1. Force-stop from Settings. Notification gone. Alarms are cancelled;
   `:listener` is dead too.
2. **Do not open the app.** Wait up to ~2 minutes.

   **Pass:** OS rebinds the enabled listener → process starts → FGS
   returns. This is the Nothing X path and is OEM-dependent.

   **Acceptable miss:** nothing happens until you launch the app. A
   package FORCE_STOP is allowed to win; record the OEM. Then confirm that
   launching the app *does* bring the service back (and on vivo, §8's
   guidance page may appear).

## 7. Phone alerts on the bot — two phones, connected

Notification access is a real feature, not only a keep-alive trick. Cute
Bot never reads notification *content* — only package name + category
cross the process boundary.

1. Complete §0 so the simulator is **Connected** and **Alert access: on**.
   Leave **Show phone alerts on bot** enabled.
2. On phone #1, trigger a real, alerting notification — a message app, a
   timer, anything that would make a sound on the phone. Silent/minimized
   channels and ongoing notifications (media, downloads, our own FGS) are
   filtered out on purpose.
3. **Pass:** simulator LED **cyan blink** + **chirp**, then back to whatever
   it was showing. Companion activity log: `Phone alert: <package>`.
   Bursts are debounced (a few seconds between chirps).
4. Turn **Show phone alerts on bot** **off**. Trigger another alert.
   **Pass:** no blink/chirp. Keep-alive (§6) must still work — the
   listener stays enabled; the switch only silences the bot body.
5. **Control:** **Alert access: off** (revoke in system settings). The
   switch in the app becomes disabled. No alerts, and §6a will fail on
   vivo — expected.

## 8. OEM guidance page — vivo/iQOO only, one phone

Shown automatically **once per install** after the native side records
that the service died while it should have been running (the sticky
unexpected-death marker). Reachable any time via **Keep-alive tips** on
the service card (that button is vivo/iQOO only).

1. After a §6 swipe or a Force stop that you then recover from, open
   Companion. Expected **once:** the **Keep the bot alive** page is pushed
   on its own. Notification access is the lead action; Recents lock /
   autostart / background power are listed as extra hardening.
2. Dismiss with **Done**. Force-stop, recover, reopen several times — the
   page must **not** auto-push again.
3. **Keep-alive tips** on the service card still opens it when you choose.

**Pass:** auto-show exactly once per install; manual button still works.
On non-vivo phones the page never auto-shows and there is no
Keep-alive tips button — expected.

## Known limits (not bugs)

- **Notification timeout (~72 h):** not implemented — the plugin doesn't
  expose it; the keep-alive alarm and watchdog cover wedged-service cases
  instead.
- **API 29–30:** CDM wake-on-approach (§2) doesn't exist; watchdog + boot
  receiver + notification listener + keep-alive alarm are the resurrection
  paths there.
- **§2 timing:** "bot appeared" can take up to ~2 minutes — absence at 30 s
  is not yet a failure.
- **Bond after Remove link:** Android keeps the Bluetooth pairing until you
  forget the device in system settings.
- **Package FORCE_STOP:** cancels alarms and kills `:listener`. Recovery
  without opening the app is OEM-dependent (listener rebind). Record a
  miss; don't treat it as a failed §6a.
- **Recents lock on vivo:** does not protect against swiping that one card
  away. It only helps against "clean all".
- **Phone alerts:** no content is read. Group summaries, ongoing / FGS
  notifications, and channels below DEFAULT importance are ignored.

## Optional: developer shortcuts (laptop / wireless debugging)

Not required for this human bar. If you later connect for debugging:

- `adb logcat | grep CuteBot` — see `BotPresence`, `ensureRunning`,
  `NotifListener`, `KeepAlive`, `DefaultRelay`, `App`.
- `adb shell am force-stop com.cutebot.cute_bot` — same as Settings force
  stop.
- `adb shell cmd jobscheduler run -f com.cutebot.cute_bot <id>` — trigger
  the watchdog without waiting 15 min (`dumpsys jobscheduler | grep
  cute_bot` for the id).

Use **Settings → Developer options → Wireless debugging** if you want
these without a USB cable.
